# 2.7 Plan de respuesta a incidentes

**Incidente de referencia:** inyección SQL contra la aplicación web de TiendaCR (ataque 3 de la tabla 2.4).
**Marco:** NIST SP 800-61 (preparación, detección y análisis, contención, erradicación, recuperación y actividades posteriores), adaptado a las seis fases del enunciado.
**Técnica ATT&CK:** T1190 *Exploit Public-Facing Application* (táctica *Initial Access*). Si se extraen datos: T1005 *Data from Local System*.

---

## Roles

En un equipo de dos personas, cada integrante cubre más de un rol. El *suplente* asume el rol si el titular no está disponible.

| Rol | Responsabilidades | Titular | Suplente |
|---|---|---|---|
| **Analista SOC (N1)** | Vigilar el panel, hacer el triaje de alertas, abrir el incidente, recolectar la evidencia inicial. | Integrante 1 | Integrante 2 |
| **Responsable de incidentes (IR lead)** | Clasificar la severidad, decidir la contención, coordinar, llevar la bitácora y declarar el cierre. | Integrante 2 | Integrante 1 |
| **Administrador de sistemas** | Ejecutar la contención y la erradicación en servidores, firewall, contenedores y nginx. | Integrante 1 | Integrante 2 |
| **Dueño del negocio (gerencia de TiendaCR)** | Aprobar acciones que afectan la venta (sacar la tienda de línea) y la comunicación externa. | Gerencia (simulado) | — |
| **Asesoría legal / privacidad** | Evaluar si hubo datos personales expuestos y las obligaciones de notificación (Ley 8968 de Costa Rica). | Externo (simulado) | — |

## Clasificación de severidad

| Severidad | Criterio | Ejemplo en TiendaCR | Escalamiento |
|---|---|---|---|
| **SEV-1 Crítica** | Explotación exitosa con acceso a datos o ejecución de código. | La SQLi devuelve la tabla `users`; aparece una web shell (100110). | IR lead y gerencia de inmediato |
| **SEV-2 Alta** | Intento de explotación dirigido, sin evidencia de éxito. | Alertas 100122 repetidas con respuestas HTTP 200 sin datos filtrados. | IR lead en 15 min |
| **SEV-3 Media** | Reconocimiento o fuerza bruta bloqueada automáticamente. | 100120 (escaneo); 100101 con bloqueo aplicado. | Revisión en el turno |
| **SEV-4 Baja** | Evento aislado sin patrón. | Un 404 aislado. | Solo registro |

## Tiempos objetivo

Se cuentan desde la primera alerta.

| Fase | Objetivo | Referencia medida en el laboratorio |
|---|---|---|
| Detección (MTTD) | ≤ 5 min | La alerta de Suricata llega al SIEM en segundos (ver 2.4). |
| Triaje y clasificación | ≤ 15 min | — |
| Contención | ≤ 30 min (SEV-1) | El bloqueo automático por fuerza bruta tarda 1,07 s. La contención de SQLi es manual. |
| Erradicación | ≤ 4 h | — |
| Recuperación | ≤ 8 h | — |
| Informe de lecciones aprendidas | ≤ 5 días hábiles | — |

## 1. Preparación

Está ya implementada en el proyecto.

- **Visibilidad:**
  - Suricata con reglas ET Open y reglas propias (sids 1000003-1000005 para SQLi y traversal);
  - access log de nginx en el host;
  - Wazuh con la regla 100122 (nivel 12, T1190).
- **Superficie reducida (2.2):**
  - firewall con denegación por defecto;
  - la aplicación solo es accesible desde las IP del equipo;
  - la base de datos no se publica;
  - SSH solo con llaves.
- **Inventario:** IP, puertos y servicios en `docs/2.2-control-de-acceso.md`.
- **Herramientas listas:**
  - `vagrant ssh` a todos los servidores;
  - la consulta de alertas `jq` sobre `alerts.json`;
  - el provisionador `remediate` para aplicar controles rápido.
- **Plantilla de bitácora:** hora, quién, acción y evidencia. Ver el anexo al final.
- **Respaldo de la base de datos:** volumen Docker `dvwa-db` (procedimiento en la fase 6).
- **Contactos:** lista de roles de arriba. Canal de comunicación fuera de banda (teléfono) por si el sistema está comprometido.

## 2. Detección y análisis

**Disparador:** alerta **100122** (o 86601 con firma `TIENDACR SQLi`) en el panel de Wazuh. También puede llegar como alerta nativa 31103/31164 de inyección SQL en el registro web.

Pasos del analista N1:

1. Confirmar la alerta y obtener la IP de origen, la URI completa, la hora y la firma.
   ```bash
   vagrant ssh siem -c 'sudo jq -c "select(.rule.id==\"100122\")|{t:.timestamp,src:.data.src_ip,sig:.data.alert.signature,uri:.data.http.url}" /var/ossec/logs/alerts/alerts.json | tail'
   ```
2. Correlacionar con el access log de nginx. El objetivo es determinar si **tuvo éxito**: código HTTP y tamaño de respuesta mayor de lo normal.
   ```bash
   vagrant ssh target -c 'sudo grep "<IP_ORIGEN>" /var/log/nginx/tiendacr_access.log | grep -iE "union|select|%27" | tail -20'
   ```
   Si la respuesta tiene un código 200 y un tamaño mayor que una consulta legítima, se presume extracción de datos y el incidente es SEV-1.
3. Buscar actividad posterior desde la misma IP:
   - archivos nuevos (100110);
   - cambios en `authorized_keys` (100112);
   - otras alertas de nivel 10 o más.
4. Clasificar la severidad y abrir el incidente en la bitácora. Notificar al IR lead.

## 3. Contención

**Corto plazo (minutos), decide el IR lead:**

1. **Bloquear la IP de origen** en el objetivo. Se usa el mismo mecanismo que la respuesta activa, de forma manual:
   ```bash
   vagrant ssh target -c 'sudo iptables -I INPUT 1 -s <IP_ORIGEN> -j DROP'
   ```
2. **Parche virtual inmediato:** aplicar el nivel *impossible* forzado en nginx (consultas preparadas). No requiere detener la tienda.
   ```bash
   vagrant provision target --provision-with remediate
   ```
3. Si hay SEV-1 con ejecución de código, **aislar el servidor**: sacar la tienda de línea con la aprobación de la gerencia.
   ```bash
   vagrant ssh target -c 'sudo docker compose -f /opt/dvwa/compose.yml stop dvwa'
   ```

**Preservar evidencia antes de cambiar nada más:**

```bash
vagrant ssh target -c 'sudo mkdir -p /root/ir-$(date +%F) && cd /root/ir-$(date +%F) && \
  sudo cp /var/log/nginx/tiendacr_access.log /var/log/suricata/eve.json . && \
  sudo docker logs dvwa-dvwa-1 > dvwa-container.log 2>&1; \
  sudo tar czf uploads.tgz /opt/dvwa/uploads && sha256sum * > SHA256SUMS'
```

Se registran en la bitácora los hashes SHA-256, para mantener la cadena de custodia.

## 4. Erradicación

1. **Corregir la causa raíz:** consultas preparadas (nivel *impossible*) y validación de entradas. En una aplicación real: parche del código, revisión de los demás parámetros y pruebas con un escáner DAST.
2. **Cambiar las credenciales expuestas.** Si la tabla `users` fue leída, se asume que todos los hashes están comprometidos (DVWA usa MD5 sin sal):
   - reseteo forzado de las contraseñas de la aplicación;
   - cambio de la clave del usuario de base de datos (`/opt/dvwa/.env`).
3. **Buscar persistencia:**
   - archivos en `/opt/dvwa/uploads`;
   - cambios en el FIM de las últimas 24 h;
   - contenedores o procesos nuevos (`docker ps`, `ps aux`).
4. **Actualizar:** `apt upgrade` del host y `docker compose pull` de la imagen. Revisar el panel *Vulnerability Detection* del agente.
5. **Agregar detección** si el ataque usó una variante no cubierta: nueva regla en `local.rules` y despliegue con `--provision-with rules`.

## 5. Recuperación

1. Si hubo alteración de datos: restaurar la base de datos desde el último respaldo íntegro, anterior a la primera alerta.
2. Volver a levantar la aplicación con los controles aplicados:
   ```bash
   vagrant ssh target -c 'sudo docker compose -f /opt/dvwa/compose.yml --env-file /opt/dvwa/.env up -d'
   ```
3. **Verificación antes de reabrir:**
   - repetir el ataque de forma controlada (2.8) y confirmar que no devuelve datos;
   - confirmar que la alerta sigue generándose, porque la detección se mantiene;
   - comprobar que la tienda funciona.
4. **Vigilancia reforzada durante 72 h:** revisión diaria de alertas de nivel 7 o más desde la IP atacante y de cualquier alerta del grupo `tiendacr`.
5. El IR lead declara el cierre y la gerencia aprueba reabrir la tienda.

## 6. Lecciones aprendidas

Reunión en un plazo de 5 días hábiles. Preguntas guía:

- ¿Cuánto tardamos en detectar, contener y erradicar, comparado con los objetivos?
- ¿La alerta tenía suficiente contexto, como la URI y el tamaño de la respuesta?
- ¿Por qué estaba expuesta la vulnerabilidad? Por ejemplo: un nivel de seguridad bajo en producción o la falta de revisión de código.
- ¿Qué control habría evitado el incidente? Por ejemplo, un WAF como ModSecurity con OWASP CRS delante de la aplicación.

**Aplicadas en este proyecto:**

- Un IDS **detecta el intento, no el éxito**. Después de la remediación, Suricata sigue alertando aunque la consulta ya no devuelve datos. El triaje debe mirar la respuesta HTTP para separar SEV-1 de SEV-2.
- Se agregó el bloqueo de ejecución de PHP en las subidas (C3), porque una SQLi exitosa suele seguirse de la subida de una web shell.

**Obligaciones de notificación (Costa Rica):** si hubo datos personales reales expuestos, la Ley 8968 y su reglamento obligan al responsable de la base de datos a informar a los titulares afectados y a la PRODHAB. El reglamento fija un plazo de **cinco días hábiles** desde que se conoce el incidente; asesoría legal debe confirmar el plazo vigente. En este laboratorio no aplica, porque no se usan datos reales.
