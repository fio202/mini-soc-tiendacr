# 2.4 Ataques controlados y detecciones

**Origen:** `tiendacr-kali` (192.168.56.30).
**Objetivo:** `tiendacr-web` (192.168.56.10), en el estado **vulnerable** (`vagrant provision target --provision-with vulnerable`).
**Alcance y ética:** solo recursos propios del laboratorio, en una red solo-anfitrión aislada. Sin pruebas de denegación de servicio.

> **Informe:** la tabla resumen que va al PDF está en `informe/secciones/24-ataques.md`. Este documento es la guía de trabajo detallada, con los comandos de evidencia.
>
> Las tablas recogen la ejecución real del 25/11/2026 (origen `tiendacr-kali` 192.168.56.30, objetivo `tiendacr-web` en estado vulnerable). La evidencia de cada ataque está en `evidencias/`.

---

## Procedimiento de medición (igual para los 4 ataques)

1. **Antes de lanzar el ataque**, en Kali, anotar la hora de inicio:
   ```bash
   date "+%F %T"          # ej.: 2026-11-17 20:05:10
   ```
2. Ejecutar el ataque y guardar el comando exacto (ver el apartado "Comando o herramienta" de cada ataque).
3. Esperar unos 30 s y extraer de la laptop la evidencia del SIEM:
   ```bash
   python3 scripts/alertas-ataque.py 192.168.56.30 "<hora de inicio>" 3
   ```
   La salida da la **regla**, la **hora de la primera alerta**, el **T+ (tiempo hasta la alerta)**, el número de alertas y la técnica **MITRE**. Se pega en la sección del ataque.
4. Captura del panel de Wazuh. Filtro: `data.srcip: 192.168.56.30 or data.src_ip: 192.168.56.30`.
5. Captura o extracto del registro de origen (comandos en cada sección).
6. Guardar todo en `evidencias/ataqueN-*.png|txt`.

> Si la respuesta activa bloquea a Kali (ataque 2), los ataques siguientes fallarán durante **10 minutos**. Esperen o desbloqueen manualmente:
> `vagrant ssh target -c "sudo iptables -D INPUT -s 192.168.56.30 -j DROP; sudo iptables -D FORWARD -s 192.168.56.30 -j DROP"`

## Ataque 2. Fuerza bruta contra el login de la aplicación

> Se ataca el login de la aplicación y no SSH, porque SSH solo acepta llaves (2.2): con la autenticación por contraseña deshabilitada, una fuerza bruta contra SSH no tiene nada que adivinar. Esa diferencia se puede mencionar como evidencia del control.

| Campo | Valor |
|---|---|
| Hora de inicio (Kali) | 2026-11-25 17:05:50 |
| Comando o herramienta | `hydra … http-get-form /vulnerabilities/brute/` |
| Diccionario usado (tamaño) | `/usr/share/wordlists/fasttrack.txt` (262 claves) |
| Qué debe demostrar | Alertas por múltiples fallos de autenticación. |
| Regla(s) esperada(s) | 100100 por intento → **100101** a los 10 intentos en 60 s; Suricata 1000002 → 100121. |
| Regla(s) que dispararon | 100100 (por intento), 100101 (T+19,2 s), 100121 (Suricata), 100120 |
| Tiempo hasta la alerta 100101 | 19,2 s |
| Respuesta automática | `firewall-drop` bloquea a 192.168.56.30 durante 600 s. Tiempo hasta el bloqueo: 19,2 s |
| ¿El atacante obtuvo la contraseña? | No (`0 valid password found`): el bloqueo cortó a hydra |

## Ataque 4. A elección: subida de web shell y modificación de archivos del servidor

**Justificación de la elección:**

- Es la continuación natural de un acceso inicial: el atacante busca **persistencia**.
- Permite demostrar una detección de **host** (FIM), distinta de las de red de los ataques 1 a 3.
- El directorio de subidas de la aplicación está montado en el host (`/opt/dvwa/uploads`) y vigilado en **tiempo real** con `report_changes`.

| Campo | Valor |
|---|---|
| Hora de inicio (Kali) | 2026-11-25 17:04:52 |
| Comando o herramienta | subida por *File Upload* + `curl` al archivo |
| Archivo subido / modificado | `/opt/dvwa/uploads/prueba.php` |
| Qué debe demostrar | Alerta de integridad de archivos u otra detección justificada. |
| Regla(s) esperada(s) | FIM 554 → **100110** (nivel 12, archivo nuevo en subidas); 100111 si se modifica; Suricata 1000006 → **100123**. |
| Regla(s) que dispararon | 100123 (T+17,2 s), FIM 100110 (T+15,7 s), 86601 (Suricata) |
| Tiempo hasta la alerta FIM | 15,7 s |
| Hash SHA-256 del archivo (según el FIM) | `ab98b95a6a9ae5c91323e3fa24b50b44a539ce15dae91a2f9f3b57b276258aae` |
| MITRE ATT&CK | T1505.003 Server Software Component: Web Shell |
| Capturas | `evidencias/ataque4-*.png` |

Evidencia:

```bash
vagrant ssh target -c 'ls -la /opt/dvwa/uploads/; sudo sha256sum /opt/dvwa/uploads/*'
vagrant ssh siem -c 'sudo jq -c "select(.rule.id==\"100110\")|{t:.timestamp,file:.syscheck.path,sha256:.syscheck.sha256_after}" /var/ossec/logs/alerts/alerts.json | tail -3'

> La alerta del FIM no trae la IP del atacante, porque la genera el host. Para medir el T+ con el script se usa la alerta de Suricata (1000006). La del FIM se toma del comando anterior y se compara con la hora de inicio.

Salida de `alertas-ataque.py` y del FIM:

```

  Regla Niv  Primera alerta   T+ (s) Total  MITRE        Descripcion

  86601   3    17:05:09.177     17.2     1  -            Suricata: Alert - ET WEB_SERVER PHP tags in HTTP POST

Observaciones: el PHP se ejecutó (devolvió «TiendaCR prueba de integridad»), lo que confirma la necesidad del control C3 (403 a PHP en subidas).

## Conclusiones de la detección

Resultados de la ejecución del 25/11/2026:

- **Tiempo medio de detección:** ~15 s (4,1 s la SQLi; 15,7 s el FIM; 19,2 s la fuerza bruta; 21,1 s el escaneo), muy por debajo del objetivo de ≤ 5 min del plan de respuesta a incidentes (2.7).
- **Qué ataque generó más ruido y cuál fue el más silencioso.**
- **Ataques detectados por las dos capas, red (Suricata) y host (Wazuh):** el valor de la defensa en profundidad.
- **Falsos positivos observados**, si los hubo.
